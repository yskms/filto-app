# フィード自動検出（RSS Autodiscovery）設計

作成: 2026-08-15
ステータス: **実装済み（2026-08-16）**
関連: [`FeedService.md`](FeedService.md) / [`RssService.md`](RssService.md) / [`../screens/feed_add.md`](../screens/feed_add.md)

## 実装メモ（設計との差分）

- `utils/feedAutodiscovery.ts`（`extractFeedLinks`）/ `services/RssService.ts`（`fetchMetaOrBody`）/ `services/FeedService.ts`（`discoverFeedUrl` / `detectRssUrl`）/ `components/FeedCandidateModal.tsx` / `app/feed_add.tsx` に実装。
- `detectRssUrl` のフォールバックは `Promise.all` で全プローブの完了を待ってから `commonPaths` 添字最小を採用する実装（§6の「並列・最初に成功したものを採用」を、優先順位の正確さを優先する形で実現。個別5秒タイムアウトのため実質的な全体待ち時間もおよそ5秒に収まる）。
- **フォールバックはサイト直下（トップページ）らしいURL、つまり `pathname` が `/` のときだけ実行する**（`isSiteRootUrl`）。commonPaths は常にドメイン直下の絶対パスに解決されるため、記事など深いURLで実行すると「入力とは無関係にドメイン直下にたまたま存在するフィード」を正解として誤答しうる。実機で発覚（`https://note.com/{user}/n/{記事id}` を貼ると、著者のフィードではなく `https://note.com/rss` というサイト全体のフィードが返った）。深いURLでAutodiscoveryが0件のときは、素直に「見つかりませんでした」を返す（§7の0件パス）。
- 複数候補UIは新規に `FeedCandidateModal` を作成（`FeedSelectModal` はホーム絞り込み用でAPIが合わないため流用せず）。コメントフィードは一覧末尾かつバッジ表示で区別。
- README.md の「通信」記述を更新済み。

## 1. 背景と目的

### 現状

- `feed_add` は、ユーザーが入力したURLを **フィードURLそのもの** として `RssService.fetchMeta()` に渡す。サイトのトップページURLを貼るとパース失敗でエラーになる。
- `FeedService.detectRssUrl()`（`services/FeedService.ts:168`）は実装済みだが、**呼び出し元が存在しない（デッドコード）**。
- そのため実質的に「フィードURLを正確に知っている人しか登録できない」状態。

### 目的

サイトのURLを貼るだけでフィードを登録できるようにする。ジェネレーター（RSSHub 等）で生成したフィードを扱う記事の導線としても必要。

## 2. 「スクレイピング扱いになるのでは」への結論

**ならない。** 理由を明示しておく。

| 論点 | 判断 |
|---|---|
| 何を取得するか | HTMLの `<head>` にある `<link rel="alternate" type="application/rss+xml" href="...">` **1タグのみ**。本文・記事コンテンツは一切読まない |
| その `<link>` は何か | **RSS Autodiscovery**（2002年から使われている公開規約）。サイト側が「フィードはここにある」と公開するために自ら置いているタグ。読まれることが目的のメタデータ |
| スクレイピングとの差 | スクレイピング = HTMLから**コンテンツ**を抽出して自分の画面に出す行為。本設計は**フィードのURLという1個の文字列**を読むだけで、表示するのはサイトが配信しているフィードそのもの |
| 取得タイミング | **ユーザーがURLを入力して実行したときだけ**。巡回・定期クロールは一切しない |
| 他リーダーの実装 | Feedly / Inoreader / NetNewsWire など主要リーダーは全て同じことをしている。業界標準の挙動 |
| ストア審査 | 審査で問題になるのは「権利のないコンテンツの再配信」。フィードURLの発見はこれに当たらない。**リリース済みであることとは無関係に、そもそも懸念の対象ではない** |

**むしろ現行の `detectRssUrl()` のほうが行儀が悪い。** `/feed` `/rss` `/atom.xml` … と **8パスを総当たり**しており、多くは404を踏む。Autodiscovery なら **HTML 1回の取得で確定**するため、相手サーバーへの負荷はむしろ下がる。

### ただし明示しておく方針

- README の「通信: RSS取得のみ」は、**「ユーザー操作時に限り、フィード発見のためHTMLを1回取得する」** を含む形に更新する。クラウド依存が増えるわけではない。
- `robots.txt` は参照しない。ユーザー起点の単発取得であり、クローラではないため（RSSリーダーの慣行に従う）。この判断は意図的なものとして記録する。

## 3. 処理フロー

```
[feed_add] ユーザーが URL を入力して「取得」
  ↓
1. そのURLをフィードとして解釈できるか試す（現行 fetchMeta と同じ）
   └ 成功 → 確定。以降の処理なし（既存挙動を完全に維持）
  ↓ 失敗
2. 本文がHTMLらしいか判定（<html / <!doctype / <head を含む）
   └ HTMLでない → 「フィードとして解釈できません」エラー（現行と同じ）
  ↓ HTML
3. <head> から <link rel="alternate"> のフィード候補を抽出
  ↓
4. 候補数で分岐
   0件 → フォールバック: 既知パスの並列プローブ（§6）
   1件 → そのURLで fetchMeta し、成功したら確定
   複数 → 選択UIを出す（§7）
```

**重要**: ステップ1で成功する既存ケースの挙動は1バイトも変えない。自動検出は「今エラーになっているケース」の救済としてのみ動く。

## 4. HTML から候補を抽出する

### 制約

React Native には DOM がない。`fast-xml-parser` はHTMLを正しく扱えない（閉じないタグ、属性の引用符なし等で壊れる）。**正規表現で `<link>` タグだけを拾う。**

HTMLの一般パースは正規表現でやるべきではないが、本件は**単一タグの属性抽出**に限定されるため許容する。抽出対象が壊れていたら候補0件として扱えばよく、誤爆しても実害がない（後段の `fetchMeta` で必ず検証されるため）。

### 仕様

```ts
type FeedCandidate = { url: string; title?: string; type: 'rss' | 'atom' };

function extractFeedLinks(html: string, baseUrl: string): FeedCandidate[]
```

- **走査範囲**: 先頭から `</head>` まで。`</head>` が無い場合は**先頭 100KB まで**で打ち切る（巨大ページ対策）。
- **対象**: `<link ...>` のうち
  - `rel` に `alternate` を含む（`rel="alternate stylesheet"` のような複合値に注意し、空白区切りトークンとして判定）
  - `type` が `application/rss+xml` / `application/atom+xml` / `application/rdf+xml`（大文字小文字を無視）
- **属性の解釈**: 属性順は任意。引用符は `"` `'` なしの3パターンを許容。タグ名・属性名は大文字小文字を無視。
- **href の解決**: `new URL(href, resolveBase)` で絶対化する。
- **`resolveBase` の決定順**:
  1. `<head>` 内に `<base href="...">` があればそれを優先（HTML仕様上、相対URLの基準は `<base>`）。`<base>` 自体が相対の場合は `finalUrl` で絶対化してから使う
  2. なければ **リダイレクト後のURL**（`response.url`）
  3. 入力URLをそのまま基準にしてはいけない。`example.com` → `www.example.com/ja/` のようなリダイレクト後に相対パスが壊れる
- **除外**: `isValidFeedUrl()` を通さないもの（http/https以外）は捨てる。
- **重複排除**: 絶対化後のURLで一意化。
- **上限**: 先頭 **10件** まで。カテゴリごとにフィードを列挙するサイトが存在するため。

### 実装メモ

```
/<link\s+[^>]*>/gi でタグを列挙 → 各タグから属性を
/([a-z-]+)\s*=\s*("([^"]*)"|'([^']*)'|([^\s"'>]+))/gi で回収
```

`<link>` を `>` で閉じる前提でよい（`<link>` は void 要素であり、属性値に `>` が生で入ることは実質ない。入っていたら候補が壊れて0件になるだけ）。

## 5. `RssService` 側の変更

現行の `fetchMeta()` は本文を取得してパースし、失敗したら例外を投げるだけで、**本文を呼び出し側に渡さない**。自動検出のために同じURLを2回取ることは避けたい。

```ts
// 追加
async fetchMetaOrBody(url: string): Promise<
  | { kind: 'feed'; title: string; iconUrl?: string }
  | { kind: 'html'; body: string; finalUrl: string }
>
```

- 既存の `fetchMeta()` はこれを内部で呼び、`kind === 'html'` なら従来通り例外を投げる薄いラッパにする（**既存呼び出し元の互換を維持**）。
- `fetchWithTimeout()` は `response.url` を返すよう拡張する（現状は捨てている）。
- HTML判定は本文の先頭1KBを小文字化して `<!doctype html` / `<html` / `<head` のいずれかを含むか。Content-Type だけに頼らない（`text/html` を返さないサーバーがあるため）。

### 本文サイズの上限

`kind: 'html'` で返す本文は **先頭 200KB で切り詰める**（`body.slice(0, 200_000)`）。フィードは小さいが、HTMLは数MBあり得るため。

**ただし注意**: `fetchWithTimeout()` は `arrayBuffer()` で**本文全体を先に読み切る**ため、slice しても**ダウンロード自体は発生する**。真の意味で途中打ち切りするにはストリーミング読み取り（`response.body.getReader()`）が必要で、React Native の fetch 実装では安定して使えない。

したがって本設計では **「後段に渡すメモリ量を抑える」効果に留まる**ものとして扱い、過大なページ対策は主にタイムアウト（10秒）に委ねる。この割り切りは意図的なものとして記録する。

## 6. フォールバック：既知パスのプローブ

`<link>` が無いサイトのために `detectRssUrl()` は残すが、**現行実装は使えないので作り直す。**

現行の問題:

- 8パスを**直列**に試し、各10秒タイムアウト。**最悪80秒**ユーザーを待たせる。
- 成功しても失敗しても、全パスに `fetchMeta`（= 本文フル取得＋パース）を走らせる。

改修方針:

| 項目 | 変更後 |
|---|---|
| 実行 | **並列**（8本同時）。最初に成功したものを採用 |
| 個別タイムアウト | **5秒** |
| 全体予算 | **8秒**で打ち切り。超えたら候補なし |
| 優先順位 | 並列なので同時に返る可能性がある。`commonPaths` の**添字が小さいものを優先**して確定する |
| 実行条件 | Autodiscovery が0件だったときのみ |

8パスの並列リクエストは相手サーバーへの瞬間的な負荷になるため、**Autodiscovery で見つかった場合は絶対に走らせない**こと。

## 7. UI（`feed_add`）

| 候補数 | 挙動 |
|---|---|
| 1件 | URL入力欄を検出したURLに**自動で差し替え**、「`https://example.com/feed` を見つけました」と**必ず明示**する。黙って書き換えない |
| 複数 | 選択モーダルを出す。`<link>` の `title` 属性（例: 「コメントフィード」「カテゴリ: 技術」）を併記して選ばせる |
| 0件 | 「このページからフィードを見つけられませんでした。フィードURLを直接入力してください」 |

- 複数候補UIは既存の `FeedSelectModal` が流用できるか要確認。難しければMVPでは**先頭1件を自動採用**とし、選択UIは次段階に回してよい。
- 検出中は進捗表示を出す（最大8秒待たされるため）。
- WordPress は本体フィードとコメントフィード（`/comments/feed`）の両方を `<link>` に出す。これを入れないと「コメントフィードが登録される」事故が起きる。判定は**3つ全部を見る**こと:
  1. `title` 属性に `comment` / `コメント` を含む
  2. `rel` に `comments` を含む
  3. **`href` のパスに `/comments/feed` `/comments/default` を含む** ← タイトルが日本語や独自文言のテーマだと 1・2 では漏れるため、これが最も確実

  該当した候補は**除外せず末尾に回す**（コメントフィードを購読したい人もいるため、選択UIには残す）。

## 8. やらないこと（スコープ外）

- HTMLからのコンテンツ抽出（本文・タイトル・OGP画像）。**フィードURLの発見のみ**に限定する。ここを越えると本当にスクレイピングになる。
- サイト内クロール、`sitemap.xml` の探索。
- ログインが必要なページの取得。
- JSON Feed 対応（別課題。現状 RSS 1.0 / 2.0 / Atom のみ）。

## 9. テスト観点

- 既存の**デフォルトフィード139本**が、変更後も全件フィードとして直接登録できること（回帰確認の本命）
- トップページURLからの検出: WordPress系（`/feed`）、はてなブログ、Zenn、Qiita、静的サイト（`index.xml`）
- `<link>` が無いサイトでフォールバックが動くこと、かつ**8秒以内に返ること**
- リダイレクトするサイト（`example.com` → `www.example.com`）で相対hrefが正しく解決されること
- 巨大HTML（数MB）で打ち切りが効くこと
- HTMLでもフィードでもないもの（画像URL、JSON）を貼ったときに素直にエラーになること
- コメントフィードが優先採用されないこと

## 10. 参考：関連する既知の不具合

自動検出とは独立だが、`RssService` のパーサ設定に起因する不具合がある。詳細は [WBS の「既知の不具合」](../../03_dev_plan/01_wbs.md) を参照。**自動検出で登録できるフィードを増やす前に、こちらを先に直すこと**（登録できてもパースで落ちるフィードが残るため）。

対象は `RssService.ts` / `OpmlService.ts` / `scripts/verify-feeds.mjs` の**3箇所**。特に自動検出との関係で言えば、自動検出が真価を発揮するのは**はてなブログ系の個人・企業ブログ**であり、それらはまさにこの不具合で落ちる層と重なる。順序を逆にすると「検出はできたが登録できない」という最悪の体験になる。
