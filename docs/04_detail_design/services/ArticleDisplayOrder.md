## この文書の位置づけ

これは**3回目の設計**である。1回目・2回目は実装・配信後にレビューで重大な欠陥が
見つかり、いずれも取り下げた。今回は実装前にレビューを5回通し、その指摘を反映済み。

### 過去2回の実装失敗（同じ轍を踏まないため）

- **`fetched_at`（端末時計）を並び順の主キーにした** → 時計が未来にずれると記事が
  永久に最上位に固定され、しかも保持期間の削除対象にもならず復旧不能
- **保持期間の削除条件を`published_at`基準に変えた** → 月1更新のブログの記事が
  取得直後に「30日以上前」として削除され、そのフィードが永久に空になる
- **バックアップの`publishedAt`から`fetched_at`を導出した** → 2099年の日付を持つ
  記事が1件混ざると、以降すべての同期が未来の時刻に固定される
- **表示時にO(n²)の並び替えをReactのeffect内で毎回実行した** → 記事をタップする
  たびに数百ms固まり、読んでいる最中に並びが変わる
- **`CREATE INDEX IF NOT EXISTS`は名前だけで判定する** → 定義を変えても既存DBには
  反映されず、修正が無効化されていた

**共通する失敗パターン**: 並び順を「揮発性の値」や「毎回再計算される値」に結びつけた。
今回は**保存時に一度だけ確定する不変の整数**を持たせる。

**もう一つの教訓**: 「安全のための制限」が別の正しさを壊すことが繰り返し起きた
（第4版の`LIMIT 1000`もこれに該当し、要件1を実際に破壊していた）。
**制限を入れる前に、その制限が必要かを実測で確かめる。**

### 版ごとの主な変更

**第5版→第6版**
- **要件1の表現が実際の設計と矛盾していた**ため修正。採番順は`published_at`基準
  なので「上から順にFiltoが取得した新しさで並ぶ」は成立しない。正しくは

## 前提条件（ユーザー合意済み）

- 既存ユーザーの**記事データ**は捨ててよい（リリース直後でユーザーがほぼいないため）
- 破壊的変更を許容する

## 満たすべき要件

1. **新規取得分が既存記事より上に積まれる** — 更新頻度の低いサイトの記事も、
   今回の同期で新しく取れたものは上位に出る。
   **同一採番バッチ内の順序は公開日時の降順**とする
   （「上から順にFiltoが取得した新しさで並ぶ」わけではない。バッチ内は公開日時順の
   ため、前回取得した記事より公開日時が古い記事が、今回取得分として上に来ることは
   ある。これは意図した仕様）
2. **サイトがある程度バラける** — 同じサイトが連続して上位を独占しない
3. **新着が少ない時は偏ってもいい** — 1〜2サイトしか更新がなければ連続は自然
4. **取得済みの並びは動かない** — 新規分が上に積み上がるだけ
5. **同じ記事の中で、表示に使う値と並びに使う値が食い違わない**
6. **後からRSS追加時、そのフィードの記事が連続するのは許容** — 要件4を優先する

### 要件1と「表示される相対時刻」の関係（決着済み）

要件1を採る以上、新しく取得した分が上に積まれる。したがって
「19日前」の記事の下に「2時間前」の記事が来ることがある。**これは仕様として受け入れる。**
現状はその記事が遥か下に埋もれて永久に出てこないことが問題であり、そちらの解消を優先する。

## 壊してはいけないもの

- 保持期間の設定通りに動く（設定を変えていないのに大量削除が起きない）
- バックアップ復元でデータが失われない
- タップ等の操作が重くならない
- 記事を多く貯めるユーザーでも破綻しない
- 初回起動・データリセット後に記事が0件のまま復旧しない、が起きない
- フィード・フィルタ・既読設定・オンボーディング状態を壊さない

## 設計

### A. 表示順を `display_order` で確定する

`articles`テーブルに **`display_order INTEGER`（NULL許容）** を追加。
NULLは「未採番」を意味する標識とする（採番は必ず1以上になるため、NULLと採番済みが
明確に区別できる）。

`fetched_at`は並び順に使わない。保持期間の削除条件としてのみ使い続ける＝**現状維持**。
これにより`fetched_at`の意味が「保持期間判定専用」に一本化される。

#### 採番の方式（2段階）

保存は現在通りフィード単位で逐次行い、採番だけ後でまとめて行う。
なお「完了」とは**今回の同期で処理対象としたフィードの保存処理が終了すること**を指す。
一部フィードの取得が失敗しても、成功した分の採番は行う（既存のSyncServiceの
エラー分離方針を踏襲する）。

1. 挿入時は`display_order`を**NULL（未採番）**として保存する
2. 今回の同期で処理対象としたフィードの保存処理が終了した後、
   **以下の3〜6をすべて単一の`withTransactionSync`内で**実行する。
   選定と削除を別トランザクションに分けると、その間に別の書き込みが入って
   「採番した集合」と「削除した集合」がずれる余地が残るため
3. 未採番の記事を次のクエリで引く

   ```sql
   SELECT id, feed_id FROM articles
   WHERE display_order IS NULL
   ORDER BY published_at DESC, id DESC
   LIMIT 5000
   ```

   - **射影必須**: `SELECT *`にすると本文込みで数千件をメモリに載せ、この方式を
     選んだ理由そのものを潰す。`diversifyByFeed`は`feedId`しか見ない
   - **並び順必須**: 省略すると挿入順＝ワーカーの完了順になり、ネットワークが
     遅かったフィードが最上位を占有する既知バグを再現する
   - **`published_at`がNULLの記事**: SQLiteでは`DESC`指定時にNULLが最後に来る
     （実測確認済み）。つまり上限超過時に最初に切り捨てられる側になる。
     同期経路では`RssService.toIsoDateOrNow`が必ず有効な日付を埋めるためNULLは
     発生せず、壊れたバックアップ経由でのみ理論上ありうるが、復元記事は未採番
     プールに入らない（下記C参照）ため実際には発生しない
4. 3で選ばれなかった未採番記事を削除する（下記「上限の扱い」参照）。
   削除は3と同じ条件から導出する（`id NOT IN (3で得たid)` かつ `display_order IS NULL`）
5. 3で得た記事に多様性補正（`diversifyByFeed`）をかけて並べる
6. `COALESCE(MAX(display_order), 0)`を基点に、補正後の**先頭ほど大きい番号**を振る
   （`base + (N - i)`。`base + i`にすると`ORDER BY display_order DESC`でバッチ内が
   逆順に表示される）
7. トランザクションが成功して初めて同期完了を通知し、ホームがDBを読み直す

#### 上限の扱い（`MAX_UNNUMBERED_ARTICLES = 5000`）

未採番が上限を超えた場合、**上位5000件だけを採番し、それより古い未採番記事は削除する**。
「残しておいて次回採番する」方式は採らない。次回採番すると`MAX`が上がっているため
**古い記事に大きい番号が付き、新しい記事より上に来てしまう**（第4版の欠陥）。

未採番記事は「保存済みだがまだホームに出ていない」中間状態にすぎず、一度も
ユーザーの目に触れていない。通常の閲覧体験における重要度が低いと判断し、
DBを健全な状態に保つことを優先する。

**削除した記事の再取得は保証しない**。RSS側が配信件数を絞る・古い記事を落とす・
304を返す等により、二度と取得できない可能性がある。「次回同期で取り直せる」とは
言えない。

削除対象の判定基準は採番順と**完全に同じ**（`published_at DESC, id DESC`で
上位5000件から漏れたもの）にする。

**なぜ5000か（実測に基づく）**

`diversifyByFeed`の実測値（Node、記事本体は含まない`{id, feedId}`のみ）:

| 件数 | 分散したケース | 1フィードが8割を占めるケース |
|---|---|---|
| 3,850（初回同期の想定） | 2ms | 61ms |
| 6,000 | 5ms | 147ms |
| 10,000 | 12ms | 410ms |

初回同期の想定件数（77フィード×50件＝3,850）で最悪61ms。5000件でも100ms前後で、
Hermesが数倍遅いとしても、既に数十秒かかっている同期処理の一部としては許容できる。
しかもこの処理は同期完了時に1回走るだけで、ホーム表示のたびには走らない。

将来フィード上限や端末性能が変わったときに調整できるよう、定数として定義し、
この実測値を根拠としてコメントに残す。

**5000の位置づけ**: これは「5000件までしか正しく扱えない」という上限ではなく、
**未採番プールが異常に膨張した場合の非常用の歯止め**である。正常運用では
未採番が5000件に達すること自体がまれ（初回同期でも3,850件）。

#### 採番の排他

**アプリ側**: `SyncService.isRefreshing`により、同一JSランタイム内では同期が
同時に1本しか走らない。フォアグラウンド同期・起動時同期・手動更新はすべて
このランタイムで動くため、ここでは競合しない。

**別ランタイムの可能性**: バックグラウンド同期（`BackgroundSync.ts`）は
`SyncService.refresh()`をそのまま呼ぶが、headlessランタイムで動く場合
`isRefreshing`はモジュール変数のため共有されない。したがって
**アプリ側の排他だけでは不十分**。

**SQLite側**: 選定・削除・`MAX`取得・採番の書き込みまでを、**JS側の`await`を
一切挟まない単一の`withTransactionSync`**で行う。SQLiteは書き込みトランザクションを
直列化するため、別ランタイムからの同時書き込みがあっても`MAX`の二重読み取りによる
採番衝突は起きない。

**ただし「必ず待って成功する」とは限らない**。ロック競合時は`SQLITE_BUSY`等で
トランザクション自体が失敗しうる。したがって:

- 採番処理は**途中経過を外部に通知しない**（部分的に採番された状態を見せない）
- 失敗時は**ロールバックし、同期完了を通知しない**。未採番のまま残るので、
  次回同期で再試行される（自己回復する）
- `withTransactionSync`は例外時に確実に`ROLLBACK`を発行して再スローすることを
  expo-sqliteの実装で確認済み

`withTransactionAsync`は使わない（排他的アクセスを保証しないため）。

#### 「同期単位」ではなく「未採番の記事すべて」を採番する

中断で未採番が残った場合、次回の採番はそれらを今回の新規分と一緒に処理する。
つまり厳密な「同期回ごとのまとまり」は保証されない。これは意図した仕様であり、
中断からの自己回復を優先した結果である。

#### 未採番の記事はホームに表示しない

一覧クエリに`WHERE display_order IS NOT NULL`を入れる。採番前に表示すると、
採番完了後に記事が下から上へ飛ぶ（要件4違反）。同期中に一時的に見えないだけで、
採番完了と同時に正しい位置に現れる。

#### 全順序と一意性

- **不変条件**: `display_order`が重複しないことは**アプリケーション側で保証する**
  （採番は単一トランザクション内で`base + (N - i)`を振るため、構造的に重複しない）
- DB制約としてのUNIQUEは**課さない**。制約違反でINSERTが失敗すると、既存の
  `catch(_){}`に飲まれて記事が黙って欠落する方が危険なため。
  「重複を許容する」のではなく「DBには保証させず、アプリ側で保証する」という分担
- すべての一覧クエリを`ORDER BY display_order DESC, id DESC`とする。
  `id DESC`は**万一重複した場合でもSQLの結果を決定的にするためのフォールバック**で
  あり、通常の順序付けはこれに依存しない（`id`は
  `INTEGER PRIMARY KEY AUTOINCREMENT`のため安定した全順序になる）
- インデックスも`(display_order DESC, id DESC)`で作る

#### `display_order`の不変性の正確な定義

「**通常の同期で一度採番された値は、以後変更しない**」が正しい。
バックアップ復元では新たに採番される（下記C参照）。単に「不変」と書くと、
復元処理での再採番が仕様違反に見えてしまうため区別する。

#### 要件との対応

- 新しい同期ほど大きい番号 → 上に来る（要件1）
- 採番時に補正済み → バラける（要件2）
- 補正アルゴリズムの性質上、候補が少なければ連続する（要件3）
- 一度振った番号は変えない → 並びが動かない（要件4・6）
- 表示時は補正処理をしない → 操作が重くならない

**単調増加の保証**: 番号はDB内の既存最大値から採番するので、端末の時計に一切依存
しない。`COALESCE`で空テーブル時のNULLを必ず潰す（怠ると全INSERTが失敗し、既存の
`catch(_){}`が握りつぶして「初回起動で記事0件のまま復旧不能」になる。過去に同種の
P0を出している）。

**桁あふれ**: SQLiteのINTEGERは64bitのため、現実的な利用速度では枯渇しない。

### B. 移行（既存DBの扱い）

**`articles`テーブルだけ**を作り直す。フィード・フィルタ・グローバル許可キーワード・
ETag等の取得状態・オンボーディング状態・言語設定には**一切触れない**。
消えるのは記事（と既読・お気に入り）だけで、次の同期で入り直す。

- **判定は`PRAGMA user_version`**で行う。列の有無チェックでは「移行が完全に終わった」
  ことを表現できない（DDLは通ったが後続処理で落ちた場合を区別できない）。
  現在は全端末で0なので、そのまま採用できる
- **運用規則**: `CURRENT_DB_VERSION`定数を置き、
  `while (version < CURRENT_DB_VERSION) { applyMigration(version); version++ }`
  の形で段階適用する。今回は`0 → 1`のみだが、将来の追加時に
  `if (version === 0)`の羅列にならないようこの形で作る
- DDLと`PRAGMA user_version`の更新を**単一の`withTransactionSync`**にまとめる。
  途中で落ちても中途半端な状態が残らず、次回起動でやり直される
- 不要になった`idx_articles_fetched_at_published_at`は
  **`DROP INDEX IF EXISTS`**で明示的に削除する（`CREATE`しないだけでは既存端末に
  残り続け、挿入のたびにコストになる。`IF EXISTS`にすることで、そのインデックスが
  存在しない端末でも移行が失敗しない）
- **バックグラウンド同期対策**: 現在`initDatabase()`はUI側（`_layout.tsx`）からしか
  呼ばれておらず、バックグラウンドの同期タスクは初期化を経ずにDBを触る。移行前のDBに
  新しいSQLを投げると黙って失敗し続けるため、`BackgroundSync.ts`のタスク先頭でも
  `initDatabase()`を呼ぶ

#### OTA誤配信の防止（コードによるガード）

移行処理はJSに含まれるため、通常のOTA配信に同梱されうる。文書上の約束では防げないので、
**アプリのネイティブバージョンが移行を意図したバージョン以上のときだけ移行を実行する**
ガードをコードに入れる（`expo-application`の`nativeApplicationVersion`を見る）。
古いネイティブ版で動いている端末にOTAが届いても発動しない。

配信自体は破壊的変更を伴うため、ネイティブビルドを上げて通常の審査経路で出す。

### C. バックアップ復元

- バックアップ形式に`displayOrder`を任意項目として追加する
  （`BACKUP_VERSION`は据え置きでよい。読み込み判定は「新しいバージョンを弾く」だけのため）
- **復元した記事は、既存の最大値の上に普通に採番する**（ユーザー合意済み。
  復元した記事群が上位に来てよい）。モードによる分岐や負の数は使わない
- **復元における「当時の並びの再現」とは、復元対象の記事同士の相対順を維持すること**を
  指す。復元記事群全体が既存記事より上に配置されることは仕様として許容する
  （この2つは別の概念なので混同しないこと）
- したがって:
  - バックアップに`displayOrder`があれば**その相対順を保つ**（多様性補正は
    かけ直さない。当時すでに補正済みの並びであり、再補正すると当時と変わってしまう）
  - `displayOrder`が無い古い形式のバックアップのみ、公開日時の降順で採番する
- **復元は`insertMany`の中で採番まで完結させる**（未採番のまま残さない。
  残すと同期の採番処理が復元分を巻き取ってしまう）
- **大量復元時の処理時間**: 復元は`insertMany`が既に全件を単一トランザクションで
  処理しており、採番を加えても支配的なコストは変わらない（多様性補正をかけ直さない
  ため、O(n²)の処理は発生しない）。ユーザーが明示的に開始した操作であり、
  進行中の表示も出ているため、数秒のブロックは許容する
- 変更が必要なファイル: `types/Article.ts`（`displayOrder`追加）、
  `ArticleRepository`の各クエリ（SELECT対象に追加）、`insertMany`、
  `BackupService`の`BackupArticle`型と`collectBackupData`

### D. 表示側

- ホーム画面から表示時の並び替え処理を**完全に削除**する
  （`diversifyByFeed`呼び出し、`DIVERSIFY_WINDOW_SIZE`定数とも）
- 新規記事は必ず先頭に追加されるだけになるため、
  `maintainVisibleContentPosition`の前提（先頭への追加）と一致する
- **`listAll`**: `ORDER BY display_order DESC, id DESC`＋`WHERE display_order IS NOT NULL`
- **`listByFeed`**: 同上に揃える。ただし現在どこからも呼ばれていない
  （`ArticleService.getArticles`は引数なしでしか呼ばれない）ため、
  ユーザーに見える並びへの影響はない
- **`listStarred`**: **公開日時順のまま据え置く**。この関数はバックアップ出力専用で
  （ホームの★絞り込みはJS側で処理している）、ユーザーに見える並びには影響しない。
  エクスポートの並びとしては公開日時順が自然。
  **将来ユーザー向け一覧に使う場合は`display_order`順へ変更すること**を
  コード上のコメントに残す（この前提が崩れた瞬間、そこだけ旧仕様の並びになるため）
- インデックスは`(display_order DESC, id DESC)`を新しい名前で作る

## 必須テストケース

実装後、最低限これらを確認する。特に5番は第4版の設計欠陥を発見したケース、
17番は過去に実際に踏んだ不具合の再発防止。

1. 記事0件の状態から初回同期（`COALESCE`が効いているか）
2. 1フィードのみ登録、50記事
3. 77フィード、約3,850記事（初回同期の想定規模。処理時間も測る）
4. 同期途中で強制終了 → 次回同期で未採番が回収されるか
5. **未採番が5000件を超えた状態** → 順序が逆転せず、超過分が削除されるか
6. 同期中にホームを表示 → 未採番が見えないか、完了後に正しい位置に現れるか
7. 同期中にバックアップ復元
8. バックアップの置き換え復元
9. バックアップのマージ復元 → 復元分が上位に、当時の相対順で入るか
10. データリセット → 再同期
11. 保持期間の変更 → 削除 → 再取得（`fetched_at`基準のままか）
12. 既読・フィルタによる絞り込み表示
13. フィード追加（そのフィードの記事が連続してよい）
14. 移行: 旧DB（`user_version=0`）から起動 → 記事が消え、フィードは残るか
15. 移行の中断 → 次回起動でやり直されるか
16. **未採番の超過削除が保持期間削除と独立していること**
    （例: 保持期間365日／未採番6000件 → 「古いから」ではなく「上限超過だから」
    1000件が消える。逆に保持期間1日／未採番100件なら保持期間削除だけが通常通り動く）
17. **`published_at`が未来日付の記事を含む同期**
    → `display_order`が暴走しない／保持期間削除に影響しない／並びが破綻しない
    （過去に2099年問題を実際に踏んでいるため必須）
18. **`display_order`の重複検査**
    ```sql
    SELECT display_order, COUNT(*) FROM articles
    WHERE display_order IS NOT NULL
    GROUP BY display_order HAVING COUNT(*) > 1;
    ```
    が常に0件であること
19. **スクロール位置の維持**: 1000件表示中に途中までスクロールした状態で同期
    → 先頭に新着が積まれても現在位置が飛ばない
    （`maintainVisibleContentPosition`との組み合わせはSQL設計だけでは保証できない）
20. **採番トランザクション中にバックアップ復元を同時開始**
    → `display_order`の重複・記事の欠落・`SQLITE_BUSY`によるデータ消失がない

## 既知のトレードオフ（受け入れる）

- **絞り込み時に多様性が崩れる**: 補正は挿入時の集合に対してかかるため、既読を隠す・
  フィルタで絞る等で間引かれると同じフィードが隣接しうる。表示時に補正し直せば
  解決するが、それは要件4を壊すため採らない
- **バッチの境目**: ある同期回の最後の記事と次の同期回の最初の記事が同じフィードに
  なることはある
- **同期中は新着が一時的に見えない**: 採番完了まで表示しないため。数秒〜数十秒
- **多様性アルゴリズムを後から変えても、過去の記事の並びは変わらない**:
  `display_order`は単なるキャッシュではなく、**UX上の履歴そのもの**になる。
  これは要件4（取得済みの並びは動かない）を優先した必然の帰結
- **保持期限で消えた記事が再取得され、上位に現れることがある**:
  旧要件7として抑止を検討したが、実害が確認されておらず、抑止機構
  （`deleted_articles`）の複雑さに見合わないため取り下げた
- **未採番が5000件を超えると、超過分は表示されずに削除される**:
  一度もホームに出ていない記事のみが対象。ただし**再取得は保証されない**
  （RSS側が配信しなくなる可能性があるため）
